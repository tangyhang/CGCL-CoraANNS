# 补充材料提交要求与开源发布准备

## 截图明确规定的要求

1. 提交补充材料时，必须提供指向材料的 URL。
2. 使用标准、公开可访问、隐私政策清晰且有长期保存保障的平台，例如公开 GitHub 仓库。
3. 个人主页不被接受。
4. 链接的安全性或匿名访问方式若存在疑虑，会延误论文评审与接收。
5. 如果不提交用于复现的材料，必须解释合理原因，例如版权限制、商业化考虑或确实不适用。
6. “没时间”或“整理代码工作太多”不是有效理由；接收前仍需要解决可用性问题。
7. EA&B 类论文必须提交补充材料，没有上述豁免。

截图输入框中的 `open source` 只是一段文字，不能替代实际公开仓库 URL。
截图未规定必须采用某种项目结构、某种许可证，也未要求把所有数据直接上传到仓库。
“匿名访问”不应擅自解释成必须移除作者身份；具体投稿匿名政策需要以对应投稿规则为准。

## 为便于复现而采用的工程安排

以下是本项目采用的整理原则，不是截图逐条强制的要求：

- 明确的目录职责，区分系统实现、入口、依赖、实验、数据工具与测试。
- 从干净目录可执行的构建命令，以及依赖、硬件和版本说明。
- 小数据端到端示例，降低验证环境的成本。
- 记录数据格式、索引训练/构建步骤、参数来源和实验运行命令。
- 保留原始日志、实际 recall 口径和结果元数据，不用历史数值冒充新运行结果。
- 保留原许可证、上游归属和第三方声明。
- 不将大型数据、二进制、分析缓存、私人路径或临时结果混入源码。

## 发布时仍需由项目实际信息补齐的内容

- 将当前源码发布到选定的公开仓库，取得真实 URL，并确认无需账号即可访问和下载。
- 填入 CoraANNS 论文的最终作者、标题和引用信息；本项目没有生成虚构的 BibTeX。
- 补充使用的 LAION100M/Wiki88M 精确子集、数据准备方式和公开获取地址。
- 在可用 GPU 上运行 GPU 测试与正式实验，并记录实际硬件、依赖环境及索引配置。
- 对论文提交对应的源码版本建立 tag/release；如有长期归档，可同时提供归档标识。

这些信息无法仅从所给截图和源码确定。当前整理提供的是可审阅、可构建的本地源码项目，
没有代替作者发布远程仓库，也没有声称已复现论文所有性能曲线。
